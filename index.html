Deep dive

The diagnosis I'm most proud of.

Alerts that fired correctly and never arrived. The bug was four layers below where it looked.

Lab environment · individual work

Alerts firing into a void

A Django REST service on shared MySQL RDS, with alerting wired down two paths: CloudWatch for AWS, Prometheus and Alertmanager for Kubernetes. The AWS path worked. The Kubernetes path fired and vanished.

PrometheusAlertmanagerEKS TerraformPackerGitLab CI Secrets ManagerIPv6
01

The symptom

CloudWatch → SNS → Lambda posted to Slack in under 5 seconds. Alertmanager rules evaluated and fired, and nothing reached the channel.

02

Ruled out the obvious

Routing config, receiver definitions, and webhook URL all checked out. The rules were correct, so the failure was downstream of Alertmanager.

03

Read the actual error

Alertmanager logs showed context deadline exceeded — timeouts, not rejections. Nothing was refusing the request; it was never arriving.

04

Isolated the boundary

Pods reached AWS services fine over VPC endpoints, but timed out to every public IPv4 destination. Not a Slack problem — an egress problem.

05

Root cause

The cluster was IPv6-only. Slack's API is IPv4-only. Reaching it depended on a NAT64 gateway that wasn't functioning — so every alert timed out at the network layer, far below the alerting stack.

The alerting was never broken. The block was cluster-level egress infrastructure — and naming that line, between "my config" and "the platform," is what saves an on-call engineer their evening.
