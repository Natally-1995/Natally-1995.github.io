Selected work

Three migrations and a review layer.

Each one started with something that was slow, fragile, or expensive — and a number that proves it moved.

Problem

Deploys meant SSH-ing into production

Eight services deployed by hand over SSH. Thirty minutes each, worse to roll back, and hosts drifted apart over time — the same service in staging and production genuinely weren't the same. Every incident investigation ended at an undocumented change someone made months earlier.

Solution architecture
merge to main │ ├─▶ Packer build ──▶ AMI baked with app + deps │ │ │ ▼ │ SSM Parameter Store (AMI id) │ │ └─────────────────────────▶ Terraform updates launch template │ ▼ ASG instance refresh │ new hosts ──▶ ALB health check ──▶ drain old
Why not the alternatives

Configuration management fixes repeatability but not drift: the host still accumulates state between runs. Containers were the other option, and other services did move to EKS, but these eight didn't need the elasticity.

Results
Deploy time~30 min8–10 min
Rollback20–30 min5–10 min
Downtimezero
Config drift incidentsended

What it taught

Image build time became the new bottleneck. Split into a scheduled base image and a thin app layer. Moving work around doesn't remove it — you choose which step gets to be slow.

Problem

CI held production credentials

Releases went out weekly because deploying was expensive — a pipeline pushing into the cluster with someone watching, two to four hours from merge to production. Batched releases meant bigger, riskier changes. And CI held credentials that could modify production, which is a wide blast radius for a system running code from pull requests.

Solution architecture
CI ──▶ build + test ──▶ push image to ECR │ ▼ commit image tag to Helm values repo │ ┌─────────────────┴─────────────────┐ │ git is the source of truth │ └─────────────────┬─────────────────┘ ▼ Argo CD reconciles cluster │ dev ──▶ staging ──▶ prod │ drift detected ──▶ reverted automatically
Why pull over push

With push, git records intent and the cluster holds truth — they drift. With pull, git is the truth and drift self-corrects. The benefit I'd argue first, though: CI no longer needs production credentials at all.

What it taught

Someone patched a deployment by hand and Argo reverted it within a minute. Correct behaviour, and it looked like a bug to them. The rollout needed the explanation to ship before the enforcement did.

Problem

Nobody owned the bill

Spend had grown gradually rather than deliberately, which is the hard version — nothing was obviously wrong. Infrastructure gets provisioned for a launch, the launch happens, and nobody revisits whether the instance is still the right size two years later.

Method
1 utilisation data ──▶ compare against provisioned │ 2 unused resources ──▶ unattached EBS, old snapshots, │ idle load balancers, dead envs │ 3 storage lifecycle ─▶ S3 tiering, snapshot retention │ 4 monitoring ──▶ so it doesn't creep back sequencing by risk: unused ▸ storage ▸ right-size all changes through Terraform — reviewable, revertible
Why not just buy reserved capacity

Commitment discounts reward you for spending. A three-year commitment on an oversized workload locks in the wrong shape — you get a discount on waste. Right-size first, then commit.

What it taught

Some of the saving decayed as new resources appeared without the same scrutiny. Cost control isn't a project, it's a habit with a dashboard — running it as a one-off was my mistake.

Problem

CIDR blocks look like every other line in a diff

Terraform plan output is long and tedious, and the dangerous lines look exactly like the safe ones. A forced replacement, an over-broad IAM policy, a widened security group — all of it reads as ordinary config in a big diff, and human review skims.

Permission boundary
AGENT MAY AGENT MAY NOT ───────────── ───────────────── read cluster + cloud state terraform apply run terraform plan merge a pull request comment on a PR write to production draft runbooks read or rotate secrets propose a diff change IAM directly ╔═══════════════════════════╗ ║ HUMAN APPROVES + MERGES ║ ╚═══════════════════════════╝
The catch that paid for it

An agent flagged a security group rule allowing a wider CIDR range than our standard, which is approved internal services only. It had already passed human review. I checked the plan, confirmed it, and worked with the engineer to narrow the range and add a validation check so the pipeline catches that class of change earlier.

How this site is built.

Fair question to ask a platform engineer about her own site.

The stack
one file index.html — markup, styles, and behaviour no framework, no build step, no dependencies hosting GitHub Pages, static, served from main deploy git push ──▶ Pages build ──▶ live in ~60s client vanilla JS. Tabs, filters and the terminal are progressive enhancement — every number and every case study renders with scripting disabled.
Why so plain

A static site needs no pipeline, and a pipeline that exists to prove a point is the same over-engineering I spend my day removing. The interesting infrastructure decisions are in the case studies above, made against production systems where they mattered.
