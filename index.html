Selected work · Chowly

Four decisions, and what came of them.

Platform work at Chowly, a Chicago restaurant-technology company that integrates delivery marketplaces with restaurant POS systems. Each case study names the alternative I rejected and why. Open any card for the architecture.

01 / DELIVERY Immutable deploymentsPacker · Terraform · EC2 · ASG SSH → PackerPRODUCTION ACCESSView architecture →

Problem

Eight services deployed by hand over SSH. The thirty minutes was human work — connecting to each host, restarting services in sequence, validating one at a time. Hosts drifted apart over months, so the same service in staging and production genuinely weren't the same, and every incident investigation ended at an undocumented change somebody made long ago.

Architecture

merge to main→ Packer build (orders-service)→ AMI id to SSM→ Terraform→ ASG refresh→ ALB health check

Why not the alternatives

Configuration management fixes repeatability but not drift — the host still accumulates state between runs. Containers were the other option, and other services did move to EKS, but these eight didn't need the elasticity.

Result

Deploy ~30 → 8–10 min
Rollback 20–30 → 5–10 min
Downtime zero
Config drift ended

What it taught

Image build time became the new bottleneck, so we split into a scheduled base image and a thin application layer. Moving work around doesn't remove it — you choose which step gets to be slow, and deploy-time is the one that matters.

02 / GITOPS Taking production credentials out of CIArgo CD · EKS · Helm · ECR 2–4 hrs → <30 minMERGE TO PRODUCTIONView architecture →

Problem

Releases went out weekly because deploying was expensive: a pipeline pushing into the cluster with somebody watching it. Batched releases meant bigger, riskier changes and harder attribution when something broke. And CI held credentials that could modify production — a wide blast radius for a system that runs code from pull requests.

Architecture

CI build + test→ ECR→ values-prod.yaml→ Argo CD reconciles→ dev → staging → prod

Representative structure — one Helm values file per environment, not the literal repo layout.

Why pull, not push

With push, git records intent and the cluster holds truth — the two drift. With pull, git is the single source of desired state and the cluster reconciles to match it. The benefit I'd argue first, though: CI no longer needs production credentials at all.

Result

20 services migrated
Merge to prod 2–4 hrs → <30 min
CI production credentials removed
Rollback a git revert

What it taught

Someone patched a deployment by hand and Argo reverted it within a minute. Correct behaviour, and it looked like a bug to them. The rollout needed the explanation to ship before the enforcement did.

03 / FINOPS Cutting AWS waste without trading reliabilityEC2 · EBS · S3 · Terraform −18%~$60–80K A YEARView method →

Problem

Spend had grown gradually rather than deliberately, which is the hard version — nothing was obviously wrong. Infrastructure gets provisioned for a launch, the launch happens, and nobody revisits whether the instance is still the right size two years later.

Method

utilisation data→ unused resources→ storage lifecycle→ monitoring

Why not just buy reserved capacity

Commitment discounts reward you for spending. A three-year commitment on an oversized workload locks in the wrong shape — you get a discount on waste. Right-size first, then commit.

Result

Spend −18%
~$60–80K annualised
Incidents caused none
All changes via Terraform

What it taught

Some of the saving decayed as new resources appeared without the same scrutiny. Cost control isn't a project, it's a habit with a dashboard — running it as a one-off was my mistake.

04 / AI + PLATFORM AI review without production accessClaude Code · MCP · Terraform ~50 → ~20 minPLAN REVIEWView boundary →

Problem

Terraform plan output is long and tedious, and the dangerous lines look exactly like the safe ones. A forced replacement, an over-broad IAM policy, a widened security group — all of it reads as ordinary config in a big diff, and human review skims.

The permission boundary

Set out in full in the next section. The short version: the agent reads, plans and comments; a human approves and merges. I built the workflow and helped define those boundaries with my platform teammate — the constraint is deliberate, not a limitation to engineer around.

Case study: the CIDR it caught

A pull request widened a security group's ingress rule from a /16 to a /8. Both were private RFC1918 ranges — this was never about public internet exposure. The actual issue was blast radius: the /8 gave the service reachability from a much larger slice of internal network than it needed, which is a least-privilege problem, not an open-firewall one. It's also the kind of change that deterministic scanning tools don't reliably catch, since neither range is a hard-coded bad pattern like 0.0.0.0/0 — a /8 is a technically valid private range, just an unnecessarily wide one for this service.

The PR had already passed an initial human review before the agent's pass. The agent didn't block the merge or apply anything — it isn't able to. It surfaced the finding as a PR comment, for a person to weigh. A human then narrowed the rule.

Result

Plan review ~50 → ~20 min
Production access none
This finding surfaced, not auto-blocked

What it taught

An agent that can apply is an agent that can cause an incident nobody chose. The value is a consistent second read on the lines people skim, not autonomy.

How I think about platform engineering

The agent can read every environment. It can apply to none of them.

DELIVERY

Repeatable and reversible

Git is the deployment path. Merging ships; reverting rolls back. No deployment reaches production by hand.

SECURITY

Constrain blast radius

Per-service identities instead of shared credentials. Changes reviewed before they merge, not after they break.

COST

Continuously remove waste

Right-size from utilisation data, delete what nobody uses, and monitor so it doesn't drift back up.

OBSERVABILITY

Make failures understandable

Alert on symptoms, not causes. On-call should start in one place and narrow from there.

AI & platform

AI with a deliberately small blast radius.

Deciding what an agent is allowed to touch is the interesting part — not whether it can write Terraform.

Agent permissionsenforced by IAM, not by prompt
read cloud and cluster stateALLOW
terraform planALLOW
analyse diff / comment on pull requestALLOW
correlate monitoring signals with changesALLOW
draft runbooks and incident summariesALLOW
terraform applyDENY
merge pull requestDENY
write to productionDENY
read or rotate secretsDENY
modify IAM policyDENY
🔒 Deny-all on terraform apply — dev, staging, and prod No exceptions by environment

The case study above covers a real finding in detail — a security-group rule widened from a /16 to a /8. CIDR blocks in a diff look like every other line of config, and neither range trips a hard-coded rule.
