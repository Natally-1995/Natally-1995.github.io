How I think about platforms

The platform should make the safe path the easy path.

SHIP

Delivery automation

Git is the deployment path. Merging ships; reverting rolls back. Nothing reaches production by hand.

PROTECT

Security & review

Per-service identities instead of shared credentials, and infrastructure changes reviewed before they merge, not after they break.

CONTROL

Cloud cost

Right-size from utilisation data, delete what nobody uses, and monitor so it doesn't drift back up.

UNDERSTAND

Observability

Alert on symptoms, not causes. On-call should start in one place and narrow from there.

Selected work

Four decisions, and what came of them.

Each one names the alternative I rejected and why. Open any of them for the architecture.

01 — DELIVERY Immutable deploymentsPacker · Terraform · EC2 · ASG ~30 → 8–10 minDEPLOY TIME

Problem

Eight services deployed by hand over SSH. The thirty minutes was human work — connecting to each host, restarting services in sequence, validating one at a time. Hosts drifted apart over months, so the same service in staging and production genuinely weren't the same, and every incident investigation ended at an undocumented change somebody made long ago.

Architecture

merge to main→ Packer build→ AMI id to SSM→ Terraform→ ASG refresh→ ALB health check

Why not the alternatives

Configuration management fixes repeatability but not drift — the host still accumulates state between runs. Containers were the other option, and other services did move to EKS, but these eight didn't need the elasticity.

Result

Deploy ~30 → 8–10 min
Rollback 20–30 → 5–10 min
Downtime zero
Config drift ended

What it taught

Image build time became the new bottleneck, so we split into a scheduled base image and a thin application layer. Moving work around doesn't remove it — you choose which step gets to be slow, and deploy-time is the one that matters.

02 — GITOPS Taking production credentials out of CIArgo CD · EKS · Helm · ECR 2–4 hrs → <30 minMERGE TO PRODUCTION

Problem

Releases went out weekly because deploying was expensive: a pipeline pushing into the cluster with somebody watching it. Batched releases meant bigger, riskier changes and harder attribution when something broke. And CI held credentials that could modify production — a wide blast radius for a system that runs code from pull requests.

Architecture

CI build + test→ ECR→ Helm values repo→ Argo CD reconciles→ dev → staging → prod

Why pull, not push

With push, git records intent and the cluster holds truth — the two drift. With pull, git is the truth and drift corrects itself. The benefit I'd argue first, though: CI no longer needs production credentials at all.

Result

20 services migrated
Merge to prod 2–4 hrs → <30 min
Failed deploys ~10% → <3%
Rollback a git revert

What it taught

Someone patched a deployment by hand and Argo reverted it within a minute. Correct behaviour, and it looked like a bug to them. The rollout needed the explanation to ship before the enforcement did.

03 — FINOPS Cutting AWS waste without trading reliabilityEC2 · EBS · S3 · Terraform −18%~$60–80K A YEAR

Problem

Spend had grown gradually rather than deliberately, which is the hard version — nothing was obviously wrong. Infrastructure gets provisioned for a launch, the launch happens, and nobody revisits whether the instance is still the right size two years later.

Method

utilisation data→ unused resources→ storage lifecycle→ monitoring

Why not just buy reserved capacity

Commitment discounts reward you for spending. A three-year commitment on an oversized workload locks in the wrong shape — you get a discount on waste. Right-size first, then commit.

Result

Spend −18%
~$60–80K annualised
Incidents caused none
All changes via Terraform

What it taught

Some of the saving decayed as new resources appeared without the same scrutiny. Cost control isn't a project, it's a habit with a dashboard — running it as a one-off was my mistake.

04 — AI + PLATFORM AI review without production accessClaude Code · MCP · Terraform ~50 → ~20 minPLAN REVIEW

Problem

Terraform plan output is long and tedious, and the dangerous lines look exactly like the safe ones. A forced replacement, an over-broad IAM policy, a widened security group — all of it reads as ordinary config in a big diff, and human review skims.

The permission boundary

This is the whole design, and it's below in full. The short version: the agent reads, plans and comments. A human approves and merges. That constraint is deliberate, not a limitation to engineer around.

Result

Plan review ~50 → ~20 min
Production access none
Caught an over-broad CIDR

What it taught

An agent that can apply is an agent that can cause an incident nobody chose. The value is a consistent second read on the lines people skim, not autonomy.

AI & platform

What the agent may do, and what it may not.

Deciding what an agent is allowed to touch is the interesting part — not whether it can write Terraform.

The agent may
  • ✓Read cloud and cluster state
  • ✓Run terraform plan and analyse the diff
  • ✓Comment on a pull request
  • ✓Correlate monitoring signals with recent changes
  • ✓Draft runbooks and incident summaries
The agent may not
  • ✕Run terraform apply
  • ✕Merge a pull request
  • ✕Write to production
  • ✕Read or rotate secrets
  • ✕Change IAM policy
Human approves + merges

It earned its keep on a security group rule that allowed a wider CIDR range than our standard, which is approved internal services only. It had already passed human review. CIDR blocks in a diff look like every other line of config.
